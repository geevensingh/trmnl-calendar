---
name: research
description: Investigate a question against primary sources and retain reusable repository findings with a verified handoff. Use when the user wants a topic researched, docs or API facts gathered, or reading legwork delegated to a background agent.
---

Give a **background agent** a bounded question and the claims or capabilities it must establish, so you keep working while it reads. Include the repository context, selected evidence target, user write restrictions, and authorized output destinations in its assignment. The supervising agent owns the final documentation and persistence check; a delegated report alone is not that check.

Its job:

1. **Establish the target.** For versioned software, use the user's explicit target or the project's declared/locked version. If neither exists, verify and record the current stable release. Resolve its release/tag and, where available, commit SHA before investigating APIs or behavior. Keep prerelease findings separate.
2. **Follow primary sources.** Use official docs, source code, specs, and first-party APIs. For the selected version, inspect versioned documentation and tagged source/tests; default-branch search is discovery, not evidence for a released version. Label comparisons by version. For unversioned services, record the access date and relevant product, runtime, or tier.
3. **Establish behavior.** Distinguish API or serialization support from effective behavior, and documented/source-inferred behavior from execution with the selected package/runtime. Classify each requested claim or capability as **supported**, **unsupported**, or **unknown**. Support the first two with primary evidence for the selected version or service context; mark inconclusive evidence unknown rather than inferring support or absence.
4. **Retain reusable knowledge.** Conclusions, assumptions, compatibility limits, source/API behavior, and edge cases that future work in this repository is likely to depend on belong in an authoritative repository reference. Use the existing documentation conventions and domain vocabulary, and preserve relevant architectural decisions. Prefer a focused update to an existing reference; otherwise choose one focused primary note for this bounded subject. Select the destination from repository context rather than routinely asking the user to choose a path.

   Retain target versions/refs or service access date and context, primary citations, the capability/status/evidence/limitations matrix, and each unknown's smallest remaining verification. Distinguish current behavior from historical or planned behavior. Link the reference from the nearest relevant existing contract, runbook, or other entry point; reuse a suitable resolving link. Add README navigation only for broader discovery. Keep detailed findings in the reference, with a short conditional steering pointer only if reliable discovery needs it.

   Reuse an already current, discoverable reference without duplicate notes or empty commits. Inspect existing work and drafts before editing, preserve unrelated content, and report a conflict that cannot be reconciled safely. Retain safe capability conclusions without credentials, private samples, or content-excluded material; existing data-handling and access restrictions still apply.

   Explain a no-document disposition when findings are not reusable, retention is inappropriate, the user requests no file changes, or no repository destination is available. Respect an explicitly selected issue-tracker destination for specs and tickets. These branches need no forced document, repository creation/clone, or permission expansion. Keep temporary transcripts, intermediate failures, progress and execution receipts in their authorized temporary/session or tracker destination, separate from reusable conclusions.
5. **Verify the handoff.** Inspect the actual reference and at least one relevant entry-point link that resolves to it. Check that the document, its evidence and scope, and the handoff agree. A missing document, missing/broken discovery link, or generated/ignored output is not completed repository documentation. Session artifacts, Library attachments and issue comments may supplement a repository reference, or serve an explicitly justified exception; they do not replace expected repository retention.

   Report the reference path, discovery entry point, and observed persistence state in short ordinary prose. A repo-local uncommitted draft is **pending persistence**; a commit is not a verified backup, and a backed-up feature branch or PR is not integration-target delivery. For repository changes, follow the repository's existing review, validation, feature-branch backup and delivery contract before claiming review readiness. Identify full commit/PR evidence when available, and keep human landing/publication pending until the existing delivery proof is satisfied. Report failed writes, unavailable permissions or backup/publication mechanisms and unresolved conflicts plainly, without a success-shaped receipt.

Investigation is complete when every requested claim has target-matched primary support or an explicit unknown with a next verification; further investigation stays scoped to those gaps. The research handoff also requires verified, discoverable retention and truthful persistence reporting, or an explicit justified no-document/no-change disposition. Drafted or blocked documentation remains unfinished; reviewed/backed-up preparation may end at the existing ready-for-human-review stage without agent landing.
